# CODE_STYLE.md

> มาตรฐานการเขียนโค้ดภายในทีม — ใช้เป็นแนวทางบังคับสำหรับ AI Coding Assistant และวิศวกรทุกคน
> เอกสารนี้ไม่ผูกกับภาษาใดภาษาหนึ่ง แต่กำหนด "DNA" ของการเขียนโค้ดที่ต้องคงอยู่ไม่ว่าจะเขียนด้วยภาษาอะไร

---

## บทนำ: ทำไมต้องมีเอกสารนี้

โค้ดถูกอ่านมากกว่าถูกเขียนหลายสิบเท่า วิศวกรคนหนึ่งอาจเขียนฟังก์ชันหนึ่งครั้ง แต่คนอื่น (รวมถึง AI) จะต้องอ่าน แก้ไข และต่อยอดมันไปอีกหลายปี เป้าหมายของเอกสารนี้ไม่ใช่การบังคับรูปแบบผิวเผิน แต่คือการถ่ายทอด **วิธีคิด** ของวิศวกรอาวุโสที่ผ่านการเขียนระบบจริง เจอบั๊กจริง และต้อง maintain โค้ดของคนอื่นจริงมาแล้วนับไม่ถ้วน

หลักการที่ยึดตลอดทั้งเอกสาร:

- "Code is written for humans first, computers second."
- "A reader should understand the intent before understanding the implementation."
- "Simple code beats clever code."
- "Consistency is more important than personal preference."
- "Every line should justify its existence."
- "If a function cannot be explained in one sentence, it probably does too much."

เอกสารนี้จงใจ **ไม่ใช้กฎตัวเลขตายตัว** (เช่น "ฟังก์ชันห้ามเกิน 30 บรรทัด") เพราะกฎแบบนั้นสร้างพฤติกรรมหลอกระบบ (เช่น หั่นฟังก์ชันให้สั้นแต่กระจายความหมายจนตามยาก) แทนที่จะแก้ปัญหาจริง สิ่งที่สำคัญกว่าคือ **หลักการที่อยู่เบื้องหลังตัวเลข**

## 1. Coding Philosophy

**แนวคิด:** โค้ดคือการสื่อสารกับมนุษย์ในอนาคต ไม่ใช่แค่คำสั่งให้เครื่องรัน คอมไพเลอร์หรืออินเทอร์พรีเตอร์ไม่สนใจว่าตัวแปรชื่ออะไร แต่คนที่มาแก้บั๊กตอนตีสองสนใจมาก

**เหตุผล:** ต้นทุนของซอฟต์แวร์ส่วนใหญ่ไม่ได้อยู่ที่การเขียนครั้งแรก แต่อยู่ที่การอ่าน การแก้ และการต่อยอด งานของวิศวกรอาวุโสไม่ใช่ "ทำให้รันได้" แต่คือ "ทำให้คนถัดไปเข้าใจได้เร็วที่สุด"

**ตัวอย่างที่ดี:** ฟังก์ชันที่อ่านครั้งเดียวแล้วรู้เจตนาทันที แม้จะยังไม่รู้รายละเอียดการ implement

**ตัวอย่างที่ไม่ดี:** โค้ดที่ต้อง debug ทีละบรรทัดถึงจะเข้าใจว่าฟังก์ชันนี้ทำอะไรกันแน่

**คำแนะนำเพิ่มเติม:** ก่อน commit ให้ถามตัวเองว่า "ถ้าฉันลืมทุกอย่างเกี่ยวกับ context นี้แล้วมาอ่านใหม่ในอีก 6 เดือน จะเข้าใจไหม"

## 2. Readability First

**แนวคิด:** เมื่อต้องเลือกระหว่างโค้ดที่อ่านง่ายกับโค้ดที่เขียนสั้นหรือเร็วกว่าเล็กน้อย ให้เลือกอ่านง่ายเสมอ

**เหตุผล:** ความเร็วในการเขียนโค้ดครั้งแรกมีค่าเพียงครั้งเดียว แต่ความเร็วในการอ่านมีค่าทุกครั้งที่มีคนเปิดไฟล์นั้น

**ตัวอย่างที่ดี:**
```python
is_source_disabled = not source.enabled
if is_source_disabled:
    return skip_result(source)
```

**ตัวอย่างที่ไม่ดี:**
```python
if not source.enabled: return skip_result(source)  # อัดทุกอย่างไว้บรรทัดเดียวเพื่อความสั้น
```

**คำแนะนำเพิ่มเติม:** อ่านโค้ดออกเสียงเหมือนอ่านประโยคภาษาอังกฤษ ถ้าอ่านแล้วสะดุด แปลว่ายังไม่ดีพอ

## 3. Simplicity over Cleverness

**แนวคิด:** วิธีแก้ปัญหาที่ตรงไปตรงมาและคาดเดาได้ ดีกว่าวิธีแก้ปัญหาที่ฉลาดแต่ต้องคิดนาน

**เหตุผล:** โค้ดที่ "ฉลาด" มักใช้ trick เฉพาะภาษา หรือใช้ side effect ที่ไม่ชัดเจน ซึ่งสร้างภาระทางปัญญาให้คนอ่านโดยไม่จำเป็น ความฉลาดของผู้เขียนไม่ควรกลายเป็นภาระของผู้อ่าน

**ตัวอย่างที่ดี:** ใช้ loop หรือ built-in function มาตรฐานที่ทุกคนในทีมอ่านออกทันที

**ตัวอย่างที่ไม่ดี:** ใช้ bit-hack, one-liner ที่ซ้อน operator หลายชั้น หรือ regex ที่ต้องนั่งถอดรหัส เพียงเพื่อประหยัดบรรทัด

**คำแนะนำเพิ่มเติม:** ถ้าต้อง comment อธิบายว่าโค้ดบรรทัดนี้ทำงานอย่างไร นั่นคือสัญญาณว่าควรเขียนให้ตรงไปตรงมากว่านี้ ไม่ใช่เพิ่ม comment

---

## 4. Separation of Concerns

**แนวคิด:** แต่ละส่วนของระบบควรรับผิดชอบเรื่องเดียว และไม่ควรรู้รายละเอียดภายในของส่วนอื่น

**เหตุผล:** เมื่อเรื่องราวถูกแยกกันชัดเจน การแก้ไขจุดหนึ่งจะไม่กระทบจุดอื่นโดยไม่ได้ตั้งใจ และสามารถทดสอบแต่ละส่วนแยกกันได้

**ตัวอย่างที่ดี:** ชั้นดึงข้อมูล (fetch), ชั้นแปลงข้อมูล (mapping), และชั้นส่งออก (spool/API) แยกไฟล์กันชัดเจน แต่ละไฟล์รู้แค่ "input/output" ของอีกฝั่ง ไม่รู้ implementation ภายใน

**ตัวอย่างที่ไม่ดี:** ฟังก์ชันเดียวที่ทั้งดึงข้อมูลจากฐานข้อมูล แปลง format และยิง HTTP request ออกไปพร้อมกัน

**คำแนะนำเพิ่มเติม:** ถ้าฟังก์ชันหนึ่งต้อง import ทั้ง database driver และ HTTP client พร้อมกัน ให้สงสัยไว้ก่อนว่ากำลังผสมความรับผิดชอบ

---

## 5. Single Responsibility

**แนวคิด:** หน่วยของโค้ด (ฟังก์ชัน คลาส โมดูล) ควรมีเหตุผลเดียวที่ต้องเปลี่ยนแปลง

**เหตุผล:** เมื่อมีเหตุผลเดียวในการเปลี่ยน การแก้บั๊กหรือเพิ่ม feature จะไม่ต้องแตะทุกจุดในระบบ

**ตัวอย่างที่ดี:** ฟังก์ชันที่แปลง 1 แถวข้อมูลดิบให้เป็น 1 usage event ไม่ยุ่งเรื่องการเขียนไฟล์หรือส่ง API

**ตัวอย่างที่ไม่ดี:** ฟังก์ชันที่ทั้ง validate, transform, log, และ persist ในที่เดียว — ถ้ากฎ validate เปลี่ยน ต้องมาไล่หาโค้ดในฟังก์ชันยักษ์เดิม

**คำแนะนำเพิ่มเติม:** ทดสอบด้วยการอธิบายฟังก์ชันเป็นประโยคเดียว ถ้าต้องใช้คำว่า "และ" มากกว่าหนึ่งครั้ง ให้พิจารณาแยก

## 6. Code Organization

**แนวคิด:** โค้ดควรถูกจัดเรียงให้คนอ่านเจอสิ่งที่สำคัญที่สุดก่อน แล้วค่อยลงรายละเอียด

**เหตุผล:** สมองมนุษย์อ่านจากบนลงล่าง การให้ public API อยู่ด้านบนและ private helper อยู่ด้านล่างทำให้ผู้อ่านเห็น "ภาพรวม" ก่อน "รายละเอียด"

**ตัวอย่างที่ดี:** ฟังก์ชันสาธารณะอย่าง `poll_configured_sources` อยู่บนสุดของไฟล์ ตามด้วย helper ที่ขึ้นต้นด้วย underscore อยู่ด้านล่าง เรียงตามลำดับที่ถูกเรียกใช้

**ตัวอย่างที่ไม่ดี:** สลับ helper กับ public function แบบสุ่ม ทำให้ต้องเลื่อนขึ้นลงตลอดเวลาเพื่อไล่ flow

**คำแนะนำเพิ่มเติม:** จัดลำดับฟังก์ชันในไฟล์ให้ตรงกับลำดับที่ผู้อ่านจะ "เดินตาม" ความคิด ไม่ใช่ตามลำดับที่เขียนขึ้นมา

---

## 7. Folder Structure

**แนวคิด:** โครงสร้างโฟลเดอร์ควรสะท้อนโดเมนของระบบ ไม่ใช่สะท้อนชนิดของไฟล์เพียงอย่างเดียว

**เหตุผล:** เมื่อโฟลเดอร์แบ่งตามความสามารถทางธุรกิจ (เช่น `sources/`, `mapping/`, `spool/`) คนที่มาแก้ feature หนึ่งจะรู้ทันทีว่าต้องเข้าไปที่ไหน แทนที่จะต้องไล่หาไฟล์กระจัดกระจายตามประเภท

**ตัวอย่างที่ดี:**
```
client_agent/
  sources/        # ตัวดึงข้อมูลแต่ละชนิด (sql, http_json, aws_*)
  mapping.py      # การแปลง row → usage event
  spool.py        # การจัดเก็บ/archive/quarantine
  agent.py        # orchestration หลัก
```

**ตัวอย่างที่ไม่ดี:**
```
controllers/
services/
utils/
helpers/
```
ที่ทุกไฟล์ปนกันหมดโดยไม่รู้ว่าโดเมนไหนอยู่ตรงไหน

**คำแนะนำเพิ่มเติม:** ตั้งคำถามว่า "ถ้าฉันจะลบ feature นี้ทั้งหมด ต้องลบกี่โฟลเดอร์" ยิ่งน้อยยิ่งดี

## 8. File Organization

**แนวคิด:** หนึ่งไฟล์ควรเล่าเรื่องเดียวจบ ไม่ใช่รวมทุกอย่างที่ "เกี่ยวข้องกันแบบหลวมๆ"

**เหตุผล:** ไฟล์ที่ทำเรื่องเดียวทำให้ระบุตำแหน่งของบั๊กและจุดแก้ไขได้เร็ว และลด merge conflict เมื่อทำงานเป็นทีม

**ตัวอย่างที่ดี:** ไฟล์ `mapping.py` มีแค่ตรรกะการแปลงข้อมูล ไม่มีตรรกะการเชื่อมต่อ API หรือ retry logic ปนอยู่

**ตัวอย่างที่ไม่ดี:** ไฟล์เดียวที่มีทั้ง config parsing, database access, business logic และ HTTP handler รวมกัน 2000 บรรทัด

**คำแนะนำเพิ่มเติม:** ถ้าต้อง scroll เพื่อหาว่าไฟล์นี้ "จริงๆ แล้วทำหน้าที่อะไร" นานเกินไป ให้พิจารณาแยกไฟล์

## 9. Naming Convention

**แนวคิด:** ชื่อคือเอกสารที่ดีที่สุด ชื่อที่ดีทำให้ไม่ต้องมี comment เลยก็เข้าใจได้

**เหตุผล:** ชื่อผิดหรือกำกวมสร้างความเข้าใจผิดที่ตรวจจับยาก เพราะคนอ่านมักเชื่อชื่อมากกว่าอ่าน implementation ทุกครั้ง

**หลักที่ควรยึด:**
- ฟังก์ชัน: ใช้คำกริยาที่บอกการกระทำ (`fetch_rows`, `derive_event_id`, `ensure_registered`)
- ตัวแปร/ฟิลด์: ใช้คำนามที่บอกความหมาย ไม่ใช่ประเภทข้อมูล (`counter_state` ไม่ใช่ `dict1`)
- boolean: ขึ้นต้นด้วย `is_`, `has_`, `should_` เพื่อให้อ่านเป็นประโยคเงื่อนไขได้ทันที
- ชื่อควรปรับตาม "บริบทของผู้บริโภคข้อมูล" — ถ้าข้อมูลจะถูกส่งออกเป็น JSON ให้ระบบภายนอก อาจใช้ camelCase ตาม convention ของ wire format แม้ตัวโค้ดภายในใช้ snake_case ก็ได้ เพราะชื่อฟิลด์ที่ส่งออกคือ "สัญญา" กับผู้บริโภค ไม่ใช่กฎของภาษาโปรแกรม

**ตัวอย่างที่ดี:** `determine_source_high_watermark`, `is_source_disabled`

**ตัวอย่างที่ไม่ดี:** `data`, `temp`, `flag`, `handleStuff`, `x2`

**คำแนะนำเพิ่มเติม:** ถ้าคิดชื่อไม่ออก มักแปลว่ายังไม่เข้าใจหน้าที่ของสิ่งนั้นดีพอ — ให้กลับไปคิดหน้าที่ก่อนตั้งชื่อ

## 10. Function Design

**แนวคิด:** ฟังก์ชันควรมีขนาดเล็กพอที่จะเห็นภาพรวมได้โดยไม่ต้องเลื่อนหน้าจอหลายครั้ง และทำสิ่งเดียวให้จบในระดับ abstraction เดียวกัน

**เหตุผล:** ฟังก์ชันที่ผสมหลายระดับ abstraction (เช่น loop ระดับต่ำ ปนกับการตัดสินใจทางธุรกิจระดับสูง) บังคับให้ผู้อ่านสลับโหมดความคิดตลอดเวลา

**ตัวอย่างที่ดี:**
```go
func PollSource(cfg Config, src Source, state *State) (Result, error) {
    if !src.Enabled {
        return skippedResult(src), nil
    }
    rows, err := fetchRows(cfg, src, state)
    if err != nil {
        return Result{}, err
    }
    if len(rows) == 0 {
        return emptyResult(src), nil
    }
    events := mapRowsToEvents(src, rows)
    return writeAndReport(cfg, src, events)
}
```
ฟังก์ชันนี้อ่านเหมือน "สารบัญ" ของขั้นตอน ไม่ยุ่งกับรายละเอียดการ fetch หรือ map เอง

**ตัวอย่างที่ไม่ดี:** ฟังก์ชันที่ยาว 200 บรรทัด สลับไปมาระหว่าง SQL query, string parsing, และการตัดสินใจทางธุรกิจ

**คำแนะนำเพิ่มเติม:** ถ้าเลื่อน parameter หรือ return type เปลี่ยนบ่อยเพราะฟังก์ชันทำหลายอย่าง นั่นคือสัญญาณให้แยก

## 11. Class / Struct Design

**แนวคิด:** คลาสหรือ struct ควรห่อหุ้ม "สถานะ + พฤติกรรมที่เกี่ยวกับสถานะนั้นโดยตรง" เท่านั้น ไม่ใช่เป็นถุงรวมฟังก์ชันที่ไม่เกี่ยวข้องกัน

**เหตุผล:** เมื่อคลาสมีขอบเขตชัดเจน การทดสอบและแทนที่ (mock) จะทำได้ง่าย และคนอ่านรู้ทันทีว่า state ไหนถูกจัดการโดยใคร

**ตัวอย่างที่ดี:** คลาส agent ที่ห่อหุ้ม `config`, `state`, `api client` และมี method ระดับ lifecycle (`ensure_registered`, `poll_sources`, `send_heartbeat`) ส่วนฟังก์ชัน utility ที่ไม่ต้องพึ่ง state ภายใน (เช่นการแปลงชนิดข้อมูล) แยกออกไปเป็นฟังก์ชันอิสระนอกคลาส

**ตัวอย่างที่ไม่ดี:** คลาส "GodObject" ที่มี method หลายสิบตัวไม่เกี่ยวข้องกัน ตั้งแต่ parse config ไปจนถึงส่ง email

**คำแนะนำเพิ่มเติม:** ถ้า method ไม่แตะ field ของคลาสเลย ให้ย้ายออกเป็นฟังก์ชันอิสระ — นั่นเป็นสัญญาณว่ามันไม่ใช่พฤติกรรมของ object นี้จริงๆ

---

## 12. Module Design

**แนวคิด:** โมดูลควรเปิดเผยเฉพาะสิ่งที่จำเป็น (public API) และซ่อนรายละเอียดภายในทั้งหมด

**เหตุผล:** ยิ่งเปิดเผยน้อย ยิ่งเปลี่ยนแปลงภายในได้อย่างอิสระโดยไม่กระทบผู้ใช้โมดูล

**ตัวอย่างที่ดี:** โมดูล mapping เปิดเผยแค่ `map_row_to_usage_event` และ `map_rows_to_usage_events` ส่วน `_render_template`, `_counter_delta_events` เป็น private เพราะเป็นรายละเอียดการ implement

**ตัวอย่างที่ไม่ดี:** เปิดเผยทุกฟังก์ชันเป็น public "เผื่อมีใครอยากใช้" ทำให้ไม่มีขอบเขตที่ชัดเจนว่าอะไรคือ contract จริง

**คำแนะนำเพิ่มเติม:** เริ่มจากปิด (private) ทุกอย่างก่อน แล้วเปิดเฉพาะเมื่อมีความจำเป็นต้องใช้จากภายนอกจริงๆ

---

## 13. Error Handling

**แนวคิด:** ความรับผิดชอบต่อ error ควรถูกวางไว้ที่ "ชั้นที่รู้ว่าจะทำอะไรกับมัน" ไม่ใช่ทุกชั้น และ error ต้องมี context เพียงพอให้ debug ได้โดยไม่ต้องเดา

**เหตุผล:** ถ้าทุกฟังก์ชันจับ error แล้วซ่อนไว้ ระบบจะดู "เสถียร" แต่จริงๆ กำลังพังเงียบๆ ในทางกลับกัน ถ้าไม่มีชั้นไหนรับผิดชอบเลย error เล็กๆ หนึ่งจุดจะทำให้ทั้งระบบล้ม

**ตัวอย่างที่ดี:**
```python
def poll_configured_sources(config, state, names=None):
    results = []
    for source in config.sources:
        try:
            results.append(poll_source_to_spool(config=config, source=source, state=state))
        except Exception as exc:
            LOG.warning("source %s failed: %s", source.name, exc)
            results.append({"source": source.name, "error": str(exc)})
    return results
```
ฟังก์ชันย่อยโยน exception ตรงไปตรงมา ส่วน orchestrator เป็นจุดเดียวที่ตัดสินใจว่า "หนึ่ง source ล้มแล้วไม่ควรทำให้ source อื่นล้มตาม"

**ตัวอย่างที่ไม่ดี:**
```python
try:
    value = int(row["amount"])
except Exception:
    pass  # กลืน error โดยไม่บันทึกอะไรเลย ทำให้ debug ภายหลังแทบเป็นไปไม่ได้
```

**คำแนะนำเพิ่มเติม:** error message ควรตอบคำถามได้ว่า "เกิดที่ไหน" และ "เกิดกับอะไร" เช่นใส่ชื่อ source หรือ id ของ record ที่ผิดพลาดเสมอ อย่าโยน error แบบไม่มี context

## 14. Async Programming

**แนวคิด:** โค้ด asynchronous ควรอ่านเป็นลำดับเหตุการณ์ที่เข้าใจง่ายเหมือน synchronous code แม้เบื้องหลังจะขนานกัน

**เหตุผล:** โค้ด async ที่ซ้อน callback หรือ promise หลายชั้นทำให้ผู้อ่านตามลำดับเวลาที่แท้จริงไม่ได้ นำไปสู่บั๊กเรื่อง race condition ที่จับยาก

**ตัวอย่างที่ดี (TypeScript):**
```typescript
async function pollSource(source: Source): Promise<Result> {
  if (!source.enabled) return skippedResult(source);
  const rows = await fetchRows(source);
  if (rows.length === 0) return emptyResult(source);
  const events = mapRowsToEvents(source, rows);
  return writeAndReport(source, events);
}
```

**ตัวอย่างที่ไม่ดี:**
```typescript
fetchRows(source).then(rows => {
  mapRows(rows).then(events => {
    write(events).then(result => {
      report(result).then(() => { /* callback hell */ });
    });
  });
});
```

**คำแนะนำเพิ่มเติม:** ใช้ async/await หรือเทียบเท่าที่ทำให้โค้ด async อ่านเป็นเส้นตรงเสมอเมื่อภาษานั้นรองรับ หลีกเลี่ยงการซ้อน callback เกิน 1 ชั้น

## 15. Functional Style

**แนวคิด:** ใช้แนวทาง functional (pure function, immutability, expression) เมื่อทำให้โค้ดอ่านง่ายและคาดเดาผลลัพธ์ได้ง่ายขึ้น ไม่ใช่เพราะอยากตามเทรนด์

**เหตุผล:** ฟังก์ชันที่ไม่มี side effect ทดสอบง่ายกว่า และอ่านแล้วรู้ทันทีว่า input อะไรได้ output อะไร ไม่ต้องสงสัยว่ามันไปแก้ state ที่อื่นหรือเปล่า

**ตัวอย่างที่ดี:**
```python
mapped = [map_row_to_usage_event(source=source, row=row) for row in rows]
```
เป็น pure transformation ที่ไม่แก้ไข `rows` เดิม และอ่านรู้ผลลัพธ์ทันที

**ตัวอย่างที่ไม่ดี:**
```python
mapped = []
for row in rows:
    row["mapped"] = True  # แก้ไข object เดิมโดยไม่จำเป็น (mutation แฝง)
    mapped.append(map_row_to_usage_event(source=source, row=row))
```

**คำแนะนำเพิ่มเติม:** ใช้ pure function เป็นค่าเริ่มต้นสำหรับ logic การแปลงข้อมูล และเก็บ mutation ไว้เฉพาะจุดที่จำเป็นจริงๆ เช่นการอัปเดต state ของระบบ

---

## 16. Object Oriented Style

**แนวคิด:** ใช้ OOP เมื่อมี "สถานะที่มีอายุยืนและมีพฤติกรรมผูกกับสถานะนั้น" ไม่ใช่ใช้ class ห่อฟังก์ชัน stateless ทุกตัว

**เหตุผล:** OOP มีประโยชน์ชัดเจนเมื่อจัดการ lifecycle ของ object เช่น agent ที่มี config/state/connection คงอยู่ตลอดการทำงาน แต่ถ้าใช้ผิดที่ (เช่นห่อ pure function ไว้ใน class แล้วเรียกผ่าน `self`) จะเพิ่มความซับซ้อนโดยไม่ได้อะไรกลับมา

**ตัวอย่างที่ดี:** คลาส agent ที่ผูก state, config, api client ไว้ด้วยกัน และมี method ที่ต้องพึ่งพา state เหล่านั้นจริงๆ เช่น `send_heartbeat`, `flush_pending`

**ตัวอย่างที่ไม่ดี:** class ที่มีแต่ static-like method ที่ไม่แตะ field เลย เช่น `class StringUtils { static capitalize(s) {...} }` ทั้งที่ควรเป็นฟังก์ชันอิสระ

**คำแนะนำเพิ่มเติม:** ก่อนสร้างคลาส ถามว่า "มันมีสถานะที่ต้องคงอยู่ข้าม method call ไหม" ถ้าไม่มี ให้ใช้ฟังก์ชันอิสระแทน

---

## 17. Data Flow

**แนวคิด:** ข้อมูลควรไหลไปทิศทางเดียวที่ชัดเจน (input → transform → output) หลีกเลี่ยงการให้หลายจุดแก้ไขข้อมูลเดียวกันแบบไม่มีลำดับ

**เหตุผล:** เมื่อ data flow ชัดเจน การ debug ทำได้ด้วยการไล่ตามทิศทางเดียว ไม่ต้องเดาว่าใครแก้ข้อมูลนี้ก่อนหรือหลัง

**ตัวอย่างที่ดี:** `rows → map_rows_to_usage_events → write_spool_events → submit_batch` แต่ละขั้นรับ input จากขั้นก่อนหน้าและส่ง output ให้ขั้นถัดไปเท่านั้น

**ตัวอย่างที่ไม่ดี:** หลายฟังก์ชันแก้ global state หรือ shared dict เดียวกันแบบไม่เรียงลำดับ ทำให้ผลลัพธ์ขึ้นกับ "ใครรันก่อน"

**คำแนะนำเพิ่มเติม:** วาด data flow เป็นเส้นตรงบนกระดาษก่อนเขียนโค้ด ถ้าวาดแล้วมีเส้นย้อนกลับหรือพันกัน ให้ทบทวนสถาปัตยกรรมก่อน

---

## 18. State Management

**แนวคิด:** สถานะที่ต้อง persist ควรถูกจัดการที่จุดเดียว (single source of truth) และมี pattern การอัปเดตที่สม่ำเสมอ

**เหตุผล:** เมื่อ state กระจัดกระจายหลายที่ การ sync ให้ตรงกันยากขึ้นเรื่อยๆ และมักนำไปสู่บั๊กที่ state ไม่ตรงกันระหว่างส่วนต่างๆ ของระบบ

**ตัวอย่างที่ดี:** รูปแบบ "mutate แล้ว persist": แก้ไข field ใน state object แล้วเรียก `_persist_state()` เป็นขั้นตอนสุดท้ายเสมอ ไม่มีจุดไหนเขียนไฟล์ state ตรงๆ นอกเหนือจากจุดนี้

**ตัวอย่างที่ไม่ดี:** เขียนไฟล์ state จากหลายฟังก์ชันโดยตรง แต่ละฟังก์ชันมี logic การ serialize ของตัวเอง ทำให้แก้ format ทีต้องไล่แก้หลายที่

**คำแนะนำเพิ่มเติม:** ถ้ามีจุดเขียน state มากกว่าหนึ่งรูปแบบในระบบ ให้รวมเป็น helper เดียวและบังคับให้ทุกที่เรียกผ่าน helper นั้น

## 19. API Design

**แนวคิด:** API (ทั้ง internal function signature และ external HTTP API) ควรออกแบบจากมุมมองของผู้เรียกใช้ ไม่ใช่จากความสะดวกของผู้ implement

**เหตุผล:** API ที่ดีทำให้ผู้เรียกใช้ผิดพลาดได้ยาก (hard to misuse) และไม่ต้องอ่าน implementation ก่อนจะเรียกใช้ถูก

**ตัวอย่างที่ดี:** ใช้ keyword-only argument สำหรับพารามิเตอร์ที่มีความหมายกำกวมถ้าเรียงตามตำแหน่ง เช่น `map_row_to_usage_event(source=source, row=row)` แทน `map_row_to_usage_event(source, row)` ที่อาจสลับ argument กันโดยไม่รู้ตัว

**ตัวอย่างที่ไม่ดี:** ฟังก์ชันที่รับ parameter บวก/ลบตำแหน่งได้หลายแบบ (overload ซ้อนกันจนงง) หรือ boolean flag ที่ไม่บอกความหมาย เช่น `fetch(true, false, true)`

**คำแนะนำเพิ่มเติม:** ออกแบบ error response และ success response ให้มี "รูปร่างที่คาดเดาได้" เสมอ (เช่น มี field `status` ที่ค่าคงที่เป็น enum ไม่ใช่ string อิสระ)

## 20. SQL Style

**แนวคิด:** SQL ควรอ่านง่ายเหมือนภาษาโปรแกรมอื่น มีการจัดบรรทัดชัดเจน และไม่ผสม string concatenation กับค่าที่มาจากผู้ใช้

**เหตุผล:** SQL ที่จัดรูปแบบไม่ดีตรวจสอบ logic ยาก และการต่อ string โดยตรงเปิดช่องให้เกิด SQL injection

**ตัวอย่างที่ดี:**
```sql
SELECT
    event_time,
    meter_key,
    usage_quantity
FROM usage_events
WHERE service_id = :service_id
  AND event_time >= :cursor_time
ORDER BY event_time ASC
```

**ตัวอย่างที่ไม่ดี:**
```sql
SELECT * FROM usage_events WHERE service_id = '" + serviceId + "' AND event_time >= '" + cursor + "'"
```

**คำแนะนำเพิ่มเติม:** ใช้ parameterized query เสมอ ห้ามต่อ string ค่าที่มาจากภายนอกเข้ากับ SQL โดยตรงไม่ว่ากรณีใด

## 21. Logging

**แนวคิด:** log ควรบอกเล่า "เหตุการณ์สำคัญของระบบ" ไม่ใช่ dump ข้อมูลดิบทั้งหมดเพื่อ debug ชั่วคราว

**เหตุผล:** log ที่ดีช่วยวินิจฉัยปัญหา production ได้โดยไม่ต้อง reproduce bug เอง แต่ log ที่มากเกินไปหรือไม่มีโครงสร้างจะกลบข้อมูลสำคัญและกิน storage โดยเปล่าประโยชน์

**ตัวอย่างที่ดี:**
```python
LOG.warning("source %s failed: %s", source.name, exc)
```
สั้น มี context (ชื่อ source) และระดับความรุนแรงเหมาะสม

**ตัวอย่างที่ไม่ดี:**
```python
import json
LOG.info(json.dumps(events, indent=4))  # dump ข้อมูลทั้งก้อนทุกรอบ poll เป็น debug leftover ที่ไม่ควรอยู่ใน production
```
รูปแบบนี้เป็นเศษ debug ที่หลุดเข้าไปในโค้ด production จริง — ควรลบออกก่อน merge หรือถ้าจำเป็นต้อง log รายละเอียด ให้ใช้ log level `DEBUG` แบบมีเงื่อนไขเปิด/ปิดได้ ไม่ใช่ `INFO` ที่รันทุกครั้ง

**คำแนะนำเพิ่มเติม:** ห้ามใช้ `print()` ปนกับระบบ logging ที่มีอยู่แล้ว (`LOG.warning`, `LOG.info`) เพราะทำให้ log กระจายไปคนละช่องทาง ตรวจสอบและรวมศูนย์ไม่ได้ ก่อน commit ให้ค้นหาและลบ `print(...)` หรือ debug log ที่หลงเหลือทุกครั้ง

## 22. Comments

**แนวคิด:** comment ควรอธิบาย "ทำไม" ไม่ใช่ "ทำอะไร" เพราะ "ทำอะไร" ควรอ่านออกจากโค้ดเองอยู่แล้ว

**เหตุผล:** comment ที่อธิบายสิ่งที่โค้ดทำอยู่แล้วจะล้าสมัยทันทีที่โค้ดเปลี่ยนแต่ไม่มีใครแก้ comment ตาม กลายเป็นข้อมูลเท็จที่อันตรายกว่าไม่มี comment เลย

**ตัวอย่างที่ดี:**
```python
# ต้อง sort ตาม event_time ก่อน เพราะ counter delta คำนวณจากค่าก่อนหน้าตามลำดับเวลาจริง ไม่ใช่ลำดับที่ข้อมูลมาถึง
for event in sorted(events, key=lambda item: str(item.get("event_time") or "")):
```

**ตัวอย่างที่ไม่ดี:**
```python
# วน loop events
for event in events:
```

**คำแนะนำเพิ่มเติม:** ถ้าจะเขียน comment อธิบายว่าโค้ดทำอะไร ให้ลองเปลี่ยนชื่อฟังก์ชัน/ตัวแปรให้สื่อความหมายแทนก่อน ส่วนใหญ่จะพบว่าไม่ต้องใช้ comment เลย

## 23. Documentation

**แนวคิด:** เอกสารระดับโมดูล/ฟังก์ชันสาธารณะควรอธิบาย contract (input, output, edge case, exception ที่โยนได้) ไม่ใช่ทวนคำสั่งทีละบรรทัด

**เหตุผล:** ผู้ใช้ API ไม่ต้องการรู้ implementation ภายใน ต้องการรู้แค่ "เรียกยังไง คาดหวังอะไรได้บ้าง"

**ตัวอย่างที่ดี:**
```
map_rows_to_usage_events(source, rows, counter_state=None) -> list[UsageEvent]

แปลงข้อมูลดิบเป็น usage event ตาม mapping pattern ของ source
- ถ้า pattern เป็น counter_delta: จะคืนเฉพาะ event ที่ delta > 0 เท่านั้น (event แรกของแต่ละ counter จะไม่ถูกคืน)
- โยน ValueError ถ้า field บังคับขาดหายหรือ usage_quantity ติดลบ
```

**ตัวอย่างที่ไม่ดี:** เอกสารที่เขียนว่า "ฟังก์ชันนี้แปลง row เป็น event" โดยไม่บอก edge case สำคัญอย่างพฤติกรรมของ counter_delta ที่ event แรกจะหายไป ซึ่งเป็นจุดที่ผู้ใช้งานมักงงที่สุด

**คำแนะนำเพิ่มเติม:** เขียนเอกสารจากมุมมอง "คนที่ไม่เคยอ่าน implementation" ไม่ใช่มุมมองของคนเขียน

## 24. Refactoring

**แนวคิด:** refactor คือการเปลี่ยนโครงสร้างโดยไม่เปลี่ยนพฤติกรรม ทำเป็นขั้นเล็กๆ ที่ตรวจสอบได้ทีละก้าว ไม่ใช่เขียนใหม่ทั้งหมดในคราวเดียว

**เหตุผล:** การ refactor ทีละก้าวเล็กๆ ทำให้ตรวจจับได้ทันทีว่าขั้นไหนทำให้พฤติกรรมเปลี่ยนไปโดยไม่ตั้งใจ ในขณะที่การเขียนใหม่ทั้งหมดเสี่ยงสร้างบั๊กใหม่จำนวนมากที่หาต้นตอยาก

**ตัวอย่างที่ดี:** แยกฟังก์ชันยาวออกเป็น helper ทีละตัว รันเทสต์ผ่านทุกครั้งที่แยกเสร็จหนึ่งจุด ก่อนแยกจุดถัดไป

**ตัวอย่างที่ไม่ดี:** เขียน `poll_source_to_spool` ใหม่ทั้งฟังก์ชันพร้อมเปลี่ยน logic การนับ error ไปด้วย ทำให้แยกไม่ออกว่าบั๊กที่เจอมาจากการ refactor หรือการเปลี่ยน logic

**คำแนะนำเพิ่มเติม:** ระหว่าง refactor ถ้าพบว่า "อยากเปลี่ยน behavior ด้วยเลย" ให้แยก commit ออกจากกันเสมอ อย่าทำสองอย่างพร้อมกันใน commit เดียว

## 25. Performance

**แนวคิด:** เขียนโค้ดให้อ่านง่ายและถูกต้องก่อน แล้วค่อยปรับ performance เฉพาะจุดที่วัดแล้วว่าเป็นคอขวดจริง

**เหตุผล:** การ optimize ก่อนวัดผล (premature optimization) มักทำให้โค้ดซับซ้อนขึ้นโดยไม่ได้ประโยชน์จริง เพราะคอขวดจริงมักอยู่คนละจุดกับที่คาดไว้

**ตัวอย่างที่ดี:** เขียน mapping logic แบบ list comprehension ที่อ่านง่ายก่อน ถ้า profiling พบว่าช้าจริงในจุดที่ประมวลผลข้อมูลนับล้านแถว ค่อยพิจารณา batch processing หรือ streaming เฉพาะจุดนั้น

**ตัวอย่างที่ไม่ดี:** เขียน cache ซับซ้อนหรือ micro-optimize ทุกฟังก์ชันตั้งแต่แรกโดยไม่มีข้อมูลว่าจุดไหนช้าจริง ทำให้โค้ดอ่านยากขึ้นโดยแลกกับความเร็วที่ไม่มีใครวัดว่าคุ้มหรือไม่

**คำแนะนำเพิ่มเติม:** ทุกครั้งที่ optimize เพื่อ performance ให้แนบผลการวัด (benchmark) ไว้ใน commit message หรือ PR description เสมอ

## 26. Memory Usage

**แนวคิด:** จัดการหน่วยความจำด้วยการควบคุมขอบเขตอายุของข้อมูล (scope) ให้ชัดเจน โดยเฉพาะกับข้อมูลที่มีขนาดใหญ่หรือไม่จำกัด

**เหตุผล:** ข้อมูลที่โตไม่จำกัด (เช่น โหลดไฟล์ทั้งหมดเข้า memory) เป็นสาเหตุหลักของ memory leak และ OOM ใน production โดยเฉพาะระบบที่รันต่อเนื่องนาน เช่น agent loop

**ตัวอย่างที่ดี:** จำกัดจำนวน event ต่อ batch ด้วย `max_events` และประมวลผลเป็นชุดๆ แทนที่จะโหลดทั้งหมดเข้า memory ครั้งเดียว

**ตัวอย่างที่ไม่ดี:** โหลดไฟล์ spool ทั้งหมดในโฟลเดอร์เข้า memory พร้อมกันโดยไม่มี limit แม้จำนวนไฟล์จะโตไม่จำกัดตามเวลา

**คำแนะนำเพิ่มเติม:** สำหรับ process ที่รันตลอดเวลา (long-running process เช่น `run_forever`) ให้ตรวจสอบว่าไม่มี collection ใดที่โตขึ้นเรื่อยๆ โดยไม่ถูกเคลียร์

## 27. Testing

**แนวคิด:** เทสต์ควรพิสูจน์ "พฤติกรรม" ของระบบ ไม่ใช่พิสูจน์ implementation detail และควรครอบคลุมทั้ง happy path และ edge case ที่สำคัญ

**เหตุผล:** เทสต์ที่ผูกกับ implementation จะพังทุกครั้งที่ refactor แม้พฤติกรรมจะไม่เปลี่ยน ทำให้ทีมกลัวการ refactor และเทสต์กลายเป็นภาระแทนที่จะเป็นความมั่นใจ

**ตัวอย่างที่ดี:**
```python
def test_counter_delta_skips_first_reading():
    events = [{"usage_quantity": 100, "event_time": "2026-01-01T00:00:00Z", ...}]
    result = map_rows_to_usage_events(source=counter_source, rows=events, counter_state={})
    assert result == []  # ค่าแรกของ counter ไม่ควรถูกคืนเป็น event เพราะยังไม่มี baseline
```
เทสต์นี้ยืนยันพฤติกรรมทางธุรกิจที่สำคัญและไม่ชัดเจนจากชื่อฟังก์ชันเพียงอย่างเดียว

**ตัวอย่างที่ไม่ดี:** เทสต์ที่ mock ทุก internal call จนเหลือแค่ตรวจว่า "ฟังก์ชัน A ถูกเรียกด้วย argument นี้" โดยไม่ตรวจผลลัพธ์จริงเลย

**คำแนะนำเพิ่มเติม:** ให้ความสำคัญกับเทสต์ของ edge case ที่ซับซ้อนและมองไม่เห็นจากชื่อฟังก์ชัน (เช่น พฤติกรรม counter_delta ข้างต้น) มากกว่าการไล่เทสต์ทุก branch แบบกลไก

## 28. Dependency Injection

**แนวคิด:** ส่ง dependency (เช่น database connection, API client, clock) เข้ามาทางพารามิเตอร์หรือ constructor แทนการสร้างขึ้นเองภายในฟังก์ชัน

**เหตุผล:** เมื่อ dependency ถูกฉีดเข้ามา สามารถแทนที่ด้วย mock หรือ fake ระหว่างเทสต์ได้ง่าย และฟังก์ชันไม่ผูกติดกับ implementation จริงของ dependency นั้น

**ตัวอย่างที่ดี:**
```python
def poll_source_to_spool(*, config: AgentConfig, source: AgentSourceConfig, state: AgentState, ...):
    ...
```
`config` และ `state` ถูกส่งเข้ามาจากภายนอกเสมอ ทำให้เทสต์ด้วย config/state จำลองได้โดยไม่ต้องแตะไฟล์จริงหรือเครือข่ายจริง

**ตัวอย่างที่ไม่ดี:**
```python
def poll_source_to_spool(source_name: str):
    config = load_config_from_disk()  # สร้าง dependency เองภายในฟังก์ชัน ทำให้ mock ไม่ได้
    state = AgentStateStore(DEFAULT_PATH).load()
    ...
```

**คำแนะนำเพิ่มเติม:** ถ้าฟังก์ชันเปิดไฟล์ ต่อฐานข้อมูล หรือสร้าง network client เองภายใน ให้พิจารณาย้ายเป็นพารามิเตอร์ที่รับเข้ามาแทน

## 29. Design Pattern

**แนวคิด:** ใช้ design pattern เป็นเครื่องมือแก้ปัญหาที่เจอจริง ไม่ใช่ใช้เพื่อโชว์ว่ารู้จัก pattern

**เหตุผล:** pattern ที่ใช้ผิดที่จะเพิ่มชั้นของ abstraction โดยไม่มีประโยชน์ ทำให้โค้ดอ่านยากขึ้นโดยไม่ได้แก้ปัญหาอะไรจริง

**ตัวอย่างที่ดี:** ใช้ strategy pattern (dispatch ตาม `source.kind`) เมื่อมีแหล่งข้อมูลหลายชนิดที่ต้อง fetch ต่างวิธีกันจริงๆ และคาดว่าจะเพิ่มชนิดใหม่ในอนาคต

**ตัวอย่างที่ไม่ดี:** สร้าง abstract factory ซ้อน builder ซ้อน visitor pattern สำหรับ logic ที่มีแค่ 2 เงื่อนไขและไม่มีแนวโน้มจะเพิ่ม

**คำแนะนำเพิ่มเติม:** ถามก่อนใช้ pattern เสมอว่า "ปัญหาที่ pattern นี้แก้คืออะไร และมีอยู่จริงในระบบนี้ไหม" ถ้าตอบไม่ได้ชัดเจน อย่าใช้

---

## 30. Anti Pattern

**แนวคิด:** รู้จักและหลีกเลี่ยงรูปแบบโค้ดที่ดูเหมือนใช้งานได้แต่สร้างปัญหาระยะยาว

**เหตุผล:** anti-pattern มักผ่าน code review ได้เพราะ "รันได้" แต่สร้างหนี้ทางเทคนิค (technical debt) ที่ต้องจ่ายคืนในภายหลังพร้อมดอกเบี้ย

**anti-pattern ที่พบบ่อยและต้องระวังเป็นพิเศษ:**
- **Debug leftover หลุดเข้า production:** เช่น `import json` กลางฟังก์ชันแล้ว log ข้อมูลทั้งก้อนออกมา หรือ `print()` ปนกับระบบ log จริง — เป็นสัญญาณว่าไม่ได้ตรวจโค้ดก่อน merge
- **ตัวแปรไร้ประโยชน์:** เช่น `result = fetch(); return result` ที่ควรเป็น `return fetch()` ตรงๆ — สร้างภาระให้ผู้อ่านคิดว่ามันมีเหตุผลพิเศษหรือไม่
- **God object / God function:** โค้ดจุดเดียวที่รับผิดชอบทุกอย่าง
- **Magic value ที่ไม่มีชื่อ:** ตัวเลขหรือ string ที่ปรากฏลอยๆ โดยไม่บอกความหมาย
- **Silent failure:** จับ exception แล้วไม่ทำอะไรเลย (`except: pass`)
- **Copy-paste ซ้ำหลายจุด:** โค้ดชุดเดียวกันถูกก็อปวางหลายที่แทนที่จะดึงเป็น helper

**คำแนะนำเพิ่มเติม:** ก่อน merge ทุกครั้ง ให้ค้นหาคำว่า `print(`, `console.log(`, `TODO`, `debug`, `test =` ในไฟล์ที่แก้ไข เพื่อจับเศษ debug ที่หลงเหลือ

## 31. Clean Architecture

**แนวคิด:** business logic ควรอยู่ตรงกลางของระบบและไม่รู้จัก framework, database, หรือ transport layer ที่อยู่รอบนอก

**เหตุผล:** เมื่อ business logic ไม่ผูกกับรายละเอียดภายนอก จะเปลี่ยน database, เปลี่ยน framework, หรือเทสต์ business logic ได้โดยไม่ต้องแตะโค้ดแกนกลางเลย

**ตัวอย่างที่ดี:** `evaluate_mapping_spec` และ `map_row_to_usage_event` เป็น pure logic ที่ไม่รู้ว่าข้อมูลมาจาก SQL, HTTP หรือ S3 — ชั้น `sources/*` เป็นคนแปลข้อมูลจากภายนอกให้อยู่ในรูปแบบ `dict[str, Any]` มาตรฐานก่อนส่งเข้า mapping layer

**ตัวอย่างที่ไม่ดี:** ฟังก์ชัน business logic ที่ import database driver โดยตรงและเรียก SQL query อยู่ในนั้นเลย ทำให้เปลี่ยนแหล่งข้อมูลไม่ได้โดยไม่แก้ business logic

**คำแนะนำเพิ่มเติม:** ทดสอบด้วยคำถาม "ถ้าเปลี่ยนจาก REST API เป็น message queue พรุ่งนี้ ต้องแก้ business logic ไหม" ถ้าคำตอบคือต้องแก้ แปลว่า layer ยังไม่แยกพอ

---

## 32. Layered Architecture

**แนวคิด:** ระบบควรแบ่งเป็นชั้นที่ชัดเจน (เช่น transport → orchestration → domain logic → persistence) และแต่ละชั้นคุยกับชั้นที่อยู่ติดกันเท่านั้น

**เหตุผล:** เมื่อชั้นถูกกำหนดชัดเจน การเปลี่ยนแปลงในชั้นหนึ่งจะไม่กระเพื่อมข้ามหลายชั้นโดยไม่คาดคิด และคนใหม่เข้าทีมจะเข้าใจว่าโค้ดชิ้นหนึ่งควรอยู่ชั้นไหน

**ตัวอย่างที่ดี:** โครงสร้าง `agent.py` (orchestration/lifecycle) → `source_runtime.py` (การประสาน poll/map/write) → `mapping.py` (domain logic การแปลงข้อมูล) → `spool.py` (persistence) แต่ละชั้นเรียกลงล่างเท่านั้น ไม่มีชั้นล่างเรียกกลับขึ้นชั้นบน

**ตัวอย่างที่ไม่ดี:** `mapping.py` import และเรียก method ของ `agent.py` โดยตรง ทำให้เกิด circular dependency และไม่รู้ว่าอะไรคือชั้นบนชั้นล่างกันแน่

**คำแนะนำเพิ่มเติม:** วาด dependency graph ระหว่างไฟล์เป็นระยะ ถ้าพบลูกศรวนกลับ (circular) ให้ถือเป็นสัญญาณเตือนที่ต้องแก้ทันที ไม่ใช่ปล่อยผ่าน

## 33. Code Review Checklist

**แนวคิด:** การรีวิวโค้ดควรเน้นตรวจสอบเจตนาและผลกระทบ ไม่ใช่แค่ตรวจ syntax หรือสไตล์ที่เครื่องมืออัตโนมัติตรวจได้อยู่แล้ว

**เหตุผล:** สไตล์ผิวเผิน (เว้นวรรค, เครื่องหมายจุลภาค) ควรให้ linter/formatter จัดการอัตโนมัติ เวลาของมนุษย์ควรใช้ตรวจสิ่งที่เครื่องมือมองไม่เห็น เช่น เจตนา, edge case, ผลกระทบต่อระบบอื่น

**สิ่งที่ต้องตรวจสอบทุกครั้ง:**
- ชื่อฟังก์ชัน/ตัวแปรสื่อความหมายตรงกับสิ่งที่มันทำจริงหรือไม่
- มี debug leftover (`print`, `import` แปลกๆ กลางฟังก์ชัน, ตัวแปรไม่ใช้) หลงเหลืออยู่หรือไม่
- error handling ครอบคลุม edge case ที่สำคัญหรือไม่ (ข้อมูลว่าง, ค่าติดลบ, ค่า null)
- การเปลี่ยนแปลงนี้กระทบ layer อื่นที่ไม่ได้แก้ในรอบนี้หรือไม่
- มีเทสต์ครอบคลุม behavior ใหม่หรือ edge case ที่แก้หรือไม่

**คำแนะนำเพิ่มเติม:** รีวิวเวอร์ควรถามตัวเองว่า "ถ้าฉันต้อง maintain โค้ดนี้เอง ฉันจะเข้าใจมันได้ในกี่นาที" มากกว่าการหาที่ติเล็กๆ น้อยๆ

## 34. Pull Request Checklist

**แนวคิด:** PR ควรเล็กพอที่รีวิวได้จบในครั้งเดียว และอธิบายเจตนาไว้ให้ชัดเจนก่อนรีวิวเวอร์ต้องเดาเอง

**เหตุผล:** PR ใหญ่ทำให้รีวิวเวอร์เหนื่อยล้าและมองข้ามปัญหาสำคัญ ในขณะที่ PR ที่มีคำอธิบายชัดเจนช่วยลดรอบการถาม-ตอบไปมา

**สิ่งที่ควรมีใน PR ทุกครั้ง:**
- คำอธิบายว่า "ทำไม" ต้องเปลี่ยน ไม่ใช่แค่ "เปลี่ยนอะไร"
- แยก commit ที่เป็น refactor ล้วนๆ ออกจาก commit ที่เปลี่ยน behavior
- ผลการทดสอบหรือ evidence ว่าไม่กระทบ feature อื่น
- รายการ risk หรือจุดที่ควรระวังเป็นพิเศษ (ถ้ามี)

**คำแนะนำเพิ่มเติม:** ถ้า PR แตะมากกว่าหนึ่งความรับผิดชอบ (เช่น ทั้ง refactor และเพิ่ม feature ใหม่) ให้แยกเป็นหลาย PR แม้จะดูเสียเวลามากขึ้นในระยะสั้น

## 35. AI Coding Rules

**แนวคิด:** AI Coding Assistant ต้องปฏิบัติตามหลักการทั้งหมดในเอกสารนี้เสมือนเป็นวิศวกรอาวุโสในทีม ไม่ใช่เครื่องมือ generate โค้ดที่ "รันได้" เพียงอย่างเดียว

**เหตุผล:** โค้ดที่ AI เขียนจะถูก merge เข้าไปอยู่ร่วมกับโค้ดของมนุษย์ในระยะยาว ถ้า AI ไม่ยึดมาตรฐานเดียวกัน จะสร้างความไม่สม่ำเสมอ (inconsistency) ที่ทำลายความน่าเชื่อถือของทั้งฐานโค้ด

**กฎที่ AI ต้องยึดเป็นพิเศษ:**
- ห้ามทิ้งเศษ debug (`print`, log ที่ dump ข้อมูลทั้งก้อน, ตัวแปรที่สร้างแล้วไม่ได้ใช้ประโยชน์) ไว้ในโค้ดที่ส่งมอบ
- ก่อนเขียนฟังก์ชันใหม่ ให้ตรวจสอบก่อนว่ามี helper ที่ทำหน้าที่เดียวกันอยู่แล้วในโค้ดเบสหรือไม่ เพื่อลดการก็อปวางซ้ำ
- ต้องอธิบายเหตุผลของการตัดสินใจสำคัญ (เช่นทำไมเลือก pattern นี้) ไว้ใน commit message หรือ PR description เมื่อไม่ชัดเจนจากโค้ดเอง
- ต้องปรับ naming convention ให้ตรงกับโค้ดที่มีอยู่แล้วในไฟล์/โมดูลเดิม ไม่ใช่ยึดความชอบส่วนตัวของ AI
- ห้ามเปลี่ยนพฤติกรรม (behavior) ของระบบโดยไม่ได้ร้องขอ แม้จะ "ดูดีกว่า" ในสายตา AI ก็ตาม
- เมื่อไม่แน่ใจระหว่างสองทางเลือก ให้เลือกทางที่สอดคล้องกับโค้ดที่มีอยู่แล้วในบริบทเดียวกันมากที่สุด

**คำแนะนำเพิ่มเติม:** AI ควรอ่านโค้ดรอบข้างก่อนเขียนเสมอ เพื่อจับ "DNA" ของโค้ดเบสนั้นๆ ก่อนตัดสินใจเรื่องสไตล์

## 36. Formatting Rules

**แนวคิด:** การจัดรูปแบบ (whitespace, indentation, การจัดบรรทัด) ควรสม่ำเสมอทั้งโปรเจกต์และปล่อยให้เครื่องมืออัตโนมัติ (formatter) จัดการ ไม่ใช่ถกเถียงกันด้วยความเห็นส่วนตัว

**เหตุผล:** การถกเถียงเรื่อง formatting เป็นการเสียเวลาที่ไม่สร้างมูลค่า เมื่อมี formatter มาตรฐานของแต่ละภาษา (เช่น gofmt, black, prettier, rustfmt) ทีมควรใช้ค่าเริ่มต้นและไม่ปรับแต่งเพิ่มโดยไม่มีเหตุผลหนักแน่น

**ตัวอย่างที่ดี:** รันทุกไฟล์ผ่าน formatter อัตโนมัติก่อน commit ทุกครั้งผ่าน pre-commit hook

**ตัวอย่างที่ไม่ดี:** สมาชิกในทีมแต่ละคนใช้ indent ไม่เท่ากัน (2 space, 4 space, tab ปนกัน) ในไฟล์เดียวกัน

**คำแนะนำเพิ่มเติม:** ถ้ามีข้อขัดแย้งเรื่อง formatting ให้ยึดค่า default ของ formatter มาตรฐานของภาษานั้นเป็นคำตัดสิน ไม่ต้องถกเถียงเพิ่ม

---

## 37. Expression vs Statement

**แนวคิด:** ใช้ expression (ค่าที่ประเมินแล้วได้ผลลัพธ์ทันที) แทน statement (คำสั่งที่มี side effect หลายขั้น) เมื่อทำให้อ่านง่ายขึ้นและลดตัวแปรชั่วคราวที่ไม่จำเป็น

**เหตุผล:** expression บังคับให้ผลลัพธ์ต้องมีค่าเสมอ ลดโอกาสลืม assign ค่าใน branch ใด branch หนึ่ง และทำให้โค้ดกระชับโดยไม่เสียความชัดเจน

**ตัวอย่างที่ดี (Rust):**
```rust
let status = if pending_count > 0 { "warning" } else { "ok" };
```

**ตัวอย่างที่ดี (Python):**
```python
value = normalize_iso(str(raw)) if raw not in (None, "") else None
```

**ตัวอย่างที่ไม่ดี:**
```python
value = None
if raw is not None and raw != "":
    value = normalize_iso(str(raw))
# มี 4 บรรทัดเพื่อทำสิ่งที่ expression เดียวทำได้ และเสี่ยงลืมกรณีขอบ
```

**คำแนะนำเพิ่มเติม:** ใช้ expression เฉพาะเมื่อยังอ่านง่าย ถ้า logic ซับซ้อนจนต้องซ้อน ternary หลายชั้น ให้กลับไปใช้ statement ที่แยกเป็นขั้นตอนชัดเจนแทน เพราะตอนนั้น expression จะกลายเป็นความฉลาดที่อ่านยาก

---

## 38. Method Chaining

**แนวคิด:** ใช้ method chaining เมื่อลำดับการแปลงข้อมูลเป็นเส้นตรงและแต่ละขั้นตอนสื่อความหมายชัดเจนในตัวเอง

**เหตุผล:** chain ที่ดีอ่านเหมือนอ่านสูตรทำอาหาร: ทำขั้นนี้ก่อน แล้วขั้นนี้ แล้วขั้นนี้ — ลดความจำเป็นในการตั้งตัวแปรชั่วคราวระหว่างทางที่ไม่มีความหมายพิเศษ

**ตัวอย่างที่ดี (TypeScript):**
```typescript
const activeNames = sources
  .filter(s => s.enabled)
  .map(s => s.name)
  .sort();
```

**ตัวอย่างที่ดี (Rust):**
```rust
let active_names: Vec<String> = sources
    .iter()
    .filter(|s| s.enabled)
    .map(|s| s.name.clone())
    .collect();
```

**ตัวอย่างที่ไม่ดี:**
```typescript
const activeNames = sources
  .filter(s => s.enabled)
  .map(s => s.name)
  .sort()
  .reverse()
  .filter(n => n.length > 0)
  .map(n => n.trim())
  .map(n => n.toLowerCase());
// chain ยาวเกินไปจนต้องอ่านหลายรอบถึงจะตามทันว่าผลลัพธ์สุดท้ายคืออะไร
```

**คำแนะนำเพิ่มเติม:** ถ้า chain ยาวเกิน 4-5 ขั้นตอนหรือแต่ละขั้นไม่ได้สื่อความหมายชัดในตัวเอง ให้แยกเป็นตัวแปรที่มีชื่อกลางทาง เพื่อให้ผู้อ่านหยุดพักและเข้าใจทีละช่วง

## 39. Builder Pattern

**แนวคิด:** ใช้ builder เมื่อ object มี parameter จำนวนมาก มีค่า default หลายตัว หรือต้องสร้างเป็นขั้นตอนที่มีเงื่อนไข

**เหตุผล:** constructor ที่รับ parameter จำนวนมากตามตำแหน่งทำให้เรียกผิดลำดับได้ง่ายและอ่านที่จุดเรียกใช้ไม่รู้เรื่อง builder แก้ปัญหานี้ด้วยการตั้งชื่อแต่ละขั้นตอนอย่างชัดเจน

**ตัวอย่างที่ดี (Go, ใช้ functional options แทน builder แบบคลาสสิก):**
```go
client := NewIngestClient(
    WithBaseURL(cfg.BaseURL),
    WithTimeout(30 * time.Second),
    WithRetries(3),
)
```

**ตัวอย่างที่ดี (Rust):**
```rust
let request = BatchRequest::builder()
    .installation_id(id)
    .events(events)
    .build()?;
```

**ตัวอย่างที่ไม่ดี:**
```rust
let request = BatchRequest::new(id, events, None, None, true, false, 30);
// ไม่มีทางรู้ได้เลยว่า true/false/30 ตัวไหนคืออะไรจากจุดเรียกใช้
```

**คำแนะนำเพิ่มเติม:** อย่าสร้าง builder สำหรับ object ที่มี field แค่ 1-2 ตัว เพราะเป็นการเพิ่มความซับซ้อนโดยไม่จำเป็น — ใช้ builder เมื่อ parameter เยอะจริงหรือมีการสร้างแบบมีเงื่อนไขจริงๆ

## 40. Default Style

**แนวคิด:** กำหนดค่า default ให้กับ field/parameter ที่ส่วนใหญ่มีค่าเดียวกันอยู่แล้ว เพื่อให้จุดเรียกใช้ระบุเฉพาะสิ่งที่แตกต่างจากปกติ

**เหตุผล:** เมื่อผู้เรียกใช้ต้องระบุทุก parameter แม้ค่าจะเหมือนเดิมเกือบทุกครั้ง จุดเรียกใช้จะรกและซ่อนสิ่งที่สำคัญจริงๆ ไว้ท่ามกลางค่า default ที่ซ้ำๆ

**ตัวอย่างที่ดี (Python):**
```python
def poll_configured_sources(*, config, state, names=None, max_events=None):
    ...

poll_configured_sources(config=config, state=state)  # กรณีปกติเรียกสั้นๆ ได้
```

**ตัวอย่างที่ดี (Rust, ใช้ trait `Default`):**
```rust
#[derive(Default)]
struct PollOptions {
    max_events: Option<usize>,
    names: Vec<String>,
}
```

**ตัวอย่างที่ไม่ดี:** บังคับให้ทุกจุดเรียกใช้ต้องส่ง `max_events=None, names=None` ซ้ำๆ ทุกครั้งทั้งที่ 90% ของการเรียกใช้ไม่ต้องการค่านี้เลย

**คำแนะนำเพิ่มเติม:** ค่า default ต้องเป็นค่าที่ "ปลอดภัยที่สุด" เสมอ (เช่น ไม่ลบข้อมูล ไม่ทำ action ที่ทำลายล้าง) ไม่ใช่ค่าที่สะดวกต่อการ implement

---

## 41. Constructor Style

**แนวคิด:** constructor ควรทำแค่การตั้งค่าเริ่มต้น (initialize) ไม่ควรมี business logic ที่ซับซ้อนหรือ side effect ที่คาดเดายาก เช่นการยิง network request

**เหตุผล:** ถ้า constructor ทำงานหนักหรือมี side effect ที่ไม่คาดคิด การสร้าง object เพื่อทดสอบหรือใช้งานบางส่วนจะยากขึ้นมาก และ error ที่เกิดจาก side effect จะดูเหมือนมาจากการสร้าง object ธรรมดา

**ตัวอย่างที่ดี:**
```python
def __init__(self, config: AgentConfig):
    self.config = config
    self.state_store = AgentStateStore(config.state_file)
    self.state = self.state_store.load()
    if self.state.source_checkpoints is None:
        self.state.source_checkpoints = {}
    # เป็นแค่ setup ค่าเริ่มต้น ไม่มีการยิง network call ออกไปหาเซิร์ฟเวอร์
```
ส่วนการลงทะเบียนกับเซิร์ฟเวอร์ (`ensure_registered`) ซึ่งมี network I/O ถูกแยกออกเป็น method ต่างหาก ไม่ใส่ไว้ใน constructor

**ตัวอย่างที่ไม่ดี:**
```python
def __init__(self, config):
    self.config = config
    self.token = requests.post("https://api.example.com/register").json()["token"]
    # ยิง network request ตั้งแต่ตอนสร้าง object ทำให้เทสต์หรือใช้งานแบบ offline ไม่ได้เลย
```

**คำแนะนำเพิ่มเติม:** ถ้า object ต้องการทรัพยากรภายนอก (network, disk I/O หนักๆ) ให้แยกเป็น factory method หรือ explicit initialization method ต่างหากจาก constructor

## 42. Return Style

**แนวคิด:** ใช้ early return เพื่อจัดการกรณีขอบ (edge case) ก่อน แล้วปล่อยให้ส่วนหลักของฟังก์ชันจัดการกับ "กรณีปกติ" แบบไม่มีการซ้อน if ลึก

**เหตุผล:** early return ลดจำนวนชั้นการซ้อน (nesting) ทำให้ผู้อ่านไม่ต้องจำเงื่อนไขหลายชั้นค้างไว้ในหัวระหว่างอ่าน โค้ดที่เหลือหลัง guard clause คือ "เส้นทางหลัก" ที่สำคัญที่สุด

**ตัวอย่างที่ดี:**
```python
def poll_source_to_spool(*, config, source, state, max_events=None):
    if not source.enabled:
        return skipped_result(source)
    rows = _fetch_rows(config=config, source=source, state=state)
    if not rows:
        return empty_result(source)
    events = map_rows_to_usage_events(source=source, rows=rows)
    if not events:
        return no_events_result(source, rows)
    return success_result(source, rows, events)
```

**ตัวอย่างที่ไม่ดี:**
```python
def poll_source_to_spool(*, config, source, state, max_events=None):
    if source.enabled:
        rows = _fetch_rows(config=config, source=source, state=state)
        if rows:
            events = map_rows_to_usage_events(source=source, rows=rows)
            if events:
                return success_result(source, rows, events)
            else:
                return no_events_result(source, rows)
        else:
            return empty_result(source)
    else:
        return skipped_result(source)
    # ซ้อน if-else 4 ชั้น ทั้งที่เนื้อหาเหมือนกับตัวอย่างที่ดีทุกประการ
```

**คำแนะนำเพิ่มเติม:** ถ้าฟังก์ชันมี indentation ลึกเกิน 2-3 ชั้นจาก if/else ให้พิจารณาแปลงเป็น guard clause ทันที

## 43. Validation Style

**แนวคิด:** validate ข้อมูลให้เร็วที่สุดเท่าที่จะทำได้ (fail fast) ที่จุดขอบของระบบ และใช้ error message ที่บอกได้ว่า field ไหนผิดและทำไม

**เหตุผล:** ถ้าปล่อยให้ข้อมูลผิดรูปแบบไหลลึกเข้าไปในระบบก่อนพัง จะ debug ยากขึ้นมากเพราะจุดที่ error เกิดกับจุดที่สาเหตุจริงอยู่ห่างกัน

**ตัวอย่างที่ดี:**
```python
for field in CANONICAL_REQUIRED_FIELDS:
    if event.get(field) in (None, ""):
        raise ValueError(f"source {source.name}: mapped event is missing required field {field}")
```
validate ทันทีหลัง mapping เสร็จ ก่อนข้อมูลจะไหลต่อไปยัง spool หรือ API และ error message บอกทั้งชื่อ source และชื่อ field ที่ขาดหาย

**ตัวอย่างที่ไม่ดี:** ปล่อยให้ event ที่ field ขาดหายไหลไปจนถึงตอนยิง API แล้วค่อยพังด้วย error ทั่วไปจากฝั่งเซิร์ฟเวอร์อย่าง "400 Bad Request" ที่ไม่บอกว่า field ไหนของ record ไหนที่ผิด

**คำแนะนำเพิ่มเติม:** ใช้รายการ field ที่ต้อง validate เป็นข้อมูล (data-driven, เช่น tuple ของชื่อ field) แทนการเขียน `if` ทีละ field ซ้ำๆ เพื่อให้เพิ่ม/ลด field ที่ต้อง validate ได้ง่ายในจุดเดียว

---

## 44. Configuration Style

**แนวคิด:** ค่า configuration ควรแยกออกจาก business logic อย่างชัดเจน โหลดครั้งเดียวตอนเริ่มระบบ และมี validation ของตัวเองก่อนถูกใช้งานจริง

**เหตุผล:** เมื่อ config แยกจาก logic ชัดเจน การเปลี่ยนพฤติกรรมระหว่าง environment (dev/staging/production) ทำได้โดยไม่ต้องแก้โค้ด และ config ที่ผิดจะถูกจับได้ตั้งแต่ตอนเริ่มระบบแทนที่จะพังกลางทางตอนใช้งานจริง

**ตัวอย่างที่ดี:** `AgentConfig` เป็น object ที่ผ่านการ parse และ validate ครบถ้วนก่อนถูกส่งเข้า `ClientIngestAgent` ทุก field ที่จำเป็นถูกตรวจสอบตั้งแต่จุดโหลด ไม่ใช่ตอนใช้งานกลางฟังก์ชันธุรกิจ

**ตัวอย่างที่ไม่ดี:** อ่านค่าจาก environment variable ตรงๆ กลางฟังก์ชัน business logic เช่น `os.environ["API_KEY"]` กระจายอยู่หลายสิบจุดทั่วโค้ดเบส ทำให้ไม่รู้ว่าระบบต้องการ config อะไรบ้างจนกว่าจะรันแล้วพัง

**คำแนะนำเพิ่มเติม:** รวมจุดอ่าน config ไว้ที่เดียวตอน bootstrap ระบบ แล้วส่งต่อเป็น object ที่ผ่านการ validate แล้วไปยังส่วนอื่นเสมอ

## 45. Constants

**แนวคิด:** ค่าคงที่ที่มีความหมายทางธุรกิจควรถูกตั้งชื่อและประกาศไว้ที่เดียว ไม่ใช่กระจายเป็นค่า literal ทั่วโค้ดเบส

**เหตุผล:** เมื่อค่าคงที่มีชื่อ ผู้อ่านเข้าใจ "ความหมาย" ของมันทันทีโดยไม่ต้องเดา และถ้าต้องเปลี่ยนค่าในอนาคต แก้จุดเดียวจบ

**ตัวอย่างที่ดี:**
```python
CANONICAL_REQUIRED_FIELDS = (
    "event_time",
    "meter_key",
    "service_id",
    "resource_id",
    "usage_quantity",
    "billing_unit",
    "ingest_source",
)
```
ประกาศไว้ที่เดียวเป็น tuple ที่มีชื่อสื่อความหมาย ใช้ซ้ำได้ทั้งไฟล์

**ตัวอย่างที่ไม่ดี:**
```python
if not event.get("event_time"): raise ValueError(...)
if not event.get("meter_key"): raise ValueError(...)
# ก็อปวางรายชื่อ field เดิมซ้ำในหลายจุดของโค้ดเบส ถ้าต้องเพิ่ม field ใหม่ต้องไล่แก้ทุกจุด
```

**คำแนะนำเพิ่มเติม:** ถ้าค่าคงที่ถูกใช้มากกว่าหนึ่งจุด ให้ยกระดับเป็นค่าคงที่ที่มีชื่อทันที แม้จะใช้แค่ 2 ครั้งก็ตาม

---

## 46. Magic Numbers

**แนวคิด:** ตัวเลขหรือค่าที่ปรากฏลอยๆ ในโค้ดโดยไม่มีคำอธิบายความหมายถือเป็น magic number ที่ควรถูกแทนที่ด้วยค่าคงที่ที่มีชื่อ

**เหตุผล:** ตัวเลขลอยๆ ทำให้ผู้อ่านต้องเดาว่ามันมาจากไหนและทำไมถึงเป็นค่านั้น และเมื่อค่าเดียวกันปรากฏหลายจุด การแก้ไขจะเสี่ยงตกหล่น

**ตัวอย่างที่ดี:**
```python
EVENT_ID_HASH_LENGTH = 24

def derive_event_id(source_name, event):
    ...
    return f"{source_name}-{sha256_hex(base)[:EVENT_ID_HASH_LENGTH]}"
```

**ตัวอย่างที่ไม่ดี:**
```python
return f"{source_name}-{sha256_hex(base)[:24]}"
# เลข 24 นี้คืออะไร ทำไมต้อง 24 ไม่มีใครรู้นอกจากคนเขียนตอนนั้น
```

**คำแนะนำเพิ่มเติม:** ข้อยกเว้นที่ไม่ถือว่าเป็น magic number คือค่าที่ชัดเจนในตัวเองอยู่แล้วจากบริบท เช่น `0` และ `1` ในการเทียบความว่างของ list — ใช้วิจารณญาณ ไม่ใช่กฎตายตัว

## 47. Generic Programming

**แนวคิด:** ใช้ generic/type parameter เมื่อ logic เดียวกันต้องทำงานกับหลายชนิดข้อมูลจริงๆ ไม่ใช่เขียน generic ล่วงหน้าเผื่ออนาคตที่ยังไม่เกิดขึ้น

**เหตุผล:** generic ที่ไม่จำเป็นเพิ่มความซับซ้อนในการอ่านโดยไม่ได้ประโยชน์ แต่เมื่อมีความต้องการใช้ซ้ำกับหลายชนิดข้อมูลจริง generic จะลดโค้ดซ้ำซ้อนได้มาก

**ตัวอย่างที่ดี (TypeScript):**
```typescript
function maxIso<T extends string | null>(a: T, b: T): string | null {
  if (!a) return b;
  if (!b) return a;
  return a > b ? a : b;
}
```
ใช้เมื่อฟังก์ชันเดียวกันต้องรองรับ `string | null` จริงๆ ตามที่ระบบต้องใช้งานจริงหลายจุด

**ตัวอย่างที่ไม่ดี:**
```typescript
function process<T, U, V>(input: T, mapper: (x: T) => U, validator: (x: U) => V): V {
  // สร้าง generic 3 ตัวสำหรับ use case ที่จริงๆ มีแค่ชนิดข้อมูลเดียวในระบบทั้งหมด
}
```

**คำแนะนำเพิ่มเติม:** เขียนแบบเจาะจงชนิดข้อมูล (concrete type) ก่อนเสมอ แล้วค่อย generalize เป็น generic เมื่อพบว่ามีการใช้ซ้ำกับชนิดข้อมูลอื่นจริงๆ อย่างน้อย 2-3 ครั้ง

## 48. Iterator Style

**แนวคิด:** ใช้ iterator/comprehension มาตรฐานของภาษาในการวนซ้ำและแปลงข้อมูล แทนการเขียน loop แบบ manual ที่สะสมผลลัพธ์ด้วยตัวแปรชั่วคราว เมื่อทำให้อ่านง่ายขึ้น

**เหตุผล:** iterator แบบมาตรฐานสื่อ "เจตนา" ของการวนซ้ำได้ชัดเจนกว่า (filter, map, reduce บอกเจตนาในตัวเอง) และลดโอกาสเกิดบั๊กจากการลืม initialize หรือ update ตัวแปรสะสม

**ตัวอย่างที่ดี (Python):**
```python
mapped = [map_row_to_usage_event(source=source, row=row) for row in rows]
```

**ตัวอย่างที่ดี (Rust):**
```rust
let mapped: Vec<UsageEvent> = rows.iter().map(|row| map_row(source, row)).collect();
```

**ตัวอย่างที่ไม่ดี:**
```python
mapped = []
i = 0
while i < len(rows):
    mapped.append(map_row_to_usage_event(source=source, row=rows[i]))
    i += 1
# เขียน loop แบบ manual โดยไม่มีเหตุผลพิเศษ ทั้งที่ comprehension สื่อเจตนาเดียวกันได้ชัดกว่าและสั้นกว่า
```

**คำแนะนำเพิ่มเติม:** ใช้ manual loop เฉพาะเมื่อต้อง break กลางทาง, ต้องจัดการ index หลายตัวพร้อมกัน, หรือ logic ซับซ้อนเกินกว่า comprehension จะอ่านง่าย

---

## 49. Collection Style

**แนวคิด:** เลือกชนิดของ collection (list, set, map/dict) ให้ตรงกับความหมายทางธุรกิจของข้อมูล ไม่ใช่เลือกตามความเคยชิน

**เหตุผล:** การเลือก collection ผิดชนิดสร้างบั๊กเชิงตรรกะที่ตรวจจับยาก เช่น ใช้ list เก็บข้อมูลที่ต้องไม่ซ้ำ (ควรใช้ set) หรือใช้ list of tuple ค้นหาด้วย key (ควรใช้ map/dict)

**ตัวอย่างที่ดี:**
```python
counter_state: dict[str, float] = {}
# key คือ combination ของ tenant/service/resource/meter/unit ที่ต้อง lookup เร็วและไม่ซ้ำ — dict คือชนิดที่ถูกต้อง
```

**ตัวอย่างที่ไม่ดี:**
```python
counter_state: list[tuple[str, float]] = []
# ต้อง loop หา key ทุกครั้งที่จะอ่านหรืออัปเดตค่า ทั้งที่ dict ทำเรื่องเดียวกันได้ใน O(1)
```

**คำแนะนำเพิ่มเติม:** ก่อนเลือก collection ให้ถามคำถามสามข้อ: ข้อมูลต้องไม่ซ้ำไหม (set), ต้องค้นหาด้วย key ไหม (map), ต้องรักษาลำดับไหม (list/ordered structure) — คำตอบจะชี้ชนิดที่ถูกต้องให้เอง

## 50. Examples

ตัวอย่างสรุปที่แสดงให้เห็นว่า DNA เดียวกัน (guard clause, ฟังก์ชันเล็กที่ทำหน้าที่เดียว, ตั้งชื่อสื่อความหมาย, แยก orchestration ออกจาก detail) นำไปใช้ได้จริงในหลายภาษา:

**Rust:**
```rust
fn poll_source(source: &Source) -> PollResult {
    if !source.enabled {
        return PollResult::skipped(source);
    }
    let rows = fetch_rows(source);
    if rows.is_empty() {
        return PollResult::empty(source);
    }
    let events = map_rows_to_events(source, &rows);
    write_and_report(source, &rows, &events)
}
```

**Python:**
```python
def poll_source(source: Source) -> PollResult:
    if not source.enabled:
        return PollResult.skipped(source)
    rows = fetch_rows(source)
    if not rows:
        return PollResult.empty(source)
    events = map_rows_to_events(source, rows)
    return write_and_report(source, rows, events)
```

**Go:**
```go
func PollSource(source Source) PollResult {
    if !source.Enabled {
        return SkippedResult(source)
    }
    rows := FetchRows(source)
    if len(rows) == 0 {
        return EmptyResult(source)
    }
    events := MapRowsToEvents(source, rows)

```

**TypeScript:**
```typescript
function pollSource(source: Source): PollResult {
```

สังเกตว่าโครงสร้างและจังหวะการอ่านเหมือนกันทุกภาษา แม้ syntax จะต่างกัน — นี่คือสิ่งที่เอกสารนี้ต้องการให้ AI ทำซ้ำได้ในทุกภาษาที่เขียน

## การตัดสินใจเมื่อกฎขัดแย้งกัน

ในการทำงานจริง หลักการต่างๆ ในเอกสารนี้จะขัดแย้งกันเองบางครั้ง เช่น โค้ดที่อ่านง่ายที่สุดอาจไม่ได้เร็วที่สุด หรือโค้ดที่ consistent กับของเดิมอาจไม่ใช่วิธีที่ถูกต้องที่สุดในทางทฤษฎี เมื่อเกิดความขัดแย้ง ให้ใช้ลำดับความสำคัญต่อไปนี้เป็นแนวทาง (จากสำคัญที่สุดไปน้อยที่สุด):

**1. Correctness (ความถูกต้อง)** — โค้ดที่อ่านง่ายแต่ผลลัพธ์ผิด ไม่มีประโยชน์อะไรเลย ความถูกต้องของ behavior คือเงื่อนไขขั้นต่ำที่ต้องมีก่อนพิจารณาเรื่องอื่นทั้งหมด ไม่มีข้อยกเว้น

**2. Readability (ความอ่านง่าย)** — เมื่อโค้ดถูกต้องแล้ว ลำดับถัดมาคือต้องมีคนอ่านและเข้าใจมันได้ เพราะโค้ดที่ถูกต้องแต่อ่านไม่ออกจะกลายเป็นโค้ดที่ผิดในไม่ช้า เนื่องจากไม่มีใครกล้าแก้ไขมันอย่างปลอดภัย

**3. Maintainability (ความง่ายต่อการดูแลรักษา)** — ต่อเนื่องจาก readability คือโค้ดต้องแก้ไข ต่อยอด และขยายได้โดยไม่ต้องเขียนใหม่ทั้งหมด นี่คือเหตุผลที่ separation of concerns และ single responsibility สำคัญกว่าความสั้นกระชับ

**4. Consistency (ความสม่ำเสมอ)** — เมื่อมีหลายวิธีที่ถูกต้องและอ่านง่ายพอกัน ให้เลือกวิธีที่สอดคล้องกับโค้ดเดิมในบริบทเดียวกัน มากกว่าเลือกตามความชอบส่วนตัว เพราะความสม่ำเสมอทั้งโค้ดเบสมีค่ามากกว่าความเห็นที่ "ดีกว่าเล็กน้อย" ของคนคนเดียว

**5. Performance (ประสิทธิภาพ)** — สำคัญเป็นลำดับสุดท้าย ไม่ใช่เพราะไม่สำคัญ แต่เพราะการเสียสละ 4 ข้อข้างต้นเพื่อ performance ควรเกิดขึ้น **เฉพาะเมื่อมีการวัดผลจริงแล้วว่าเป็นคอขวด** ไม่ใช่การเดาล่วงหน้า เมื่อจำเป็นต้อง optimize จริง ให้ทำเฉพาะจุดที่วัดแล้วว่าช้า และเขียน comment อธิบายเหตุผลของการเสียสละความอ่านง่ายไว้เสมอ เพื่อให้คนอ่านในอนาคตรู้ว่า "นี่ไม่ใช่ความประมาท แต่เป็นการตัดสินใจที่มีข้อมูลรองรับ"

**หลักปฏิบัติเมื่อไม่แน่ใจ:** ถ้ายังตัดสินใจไม่ได้ว่าจะเลือกทางไหน ให้เลือกทางที่ทำให้ **ผู้อ่านคนถัดไป** ทำงานได้ง่ายที่สุด เพราะสุดท้ายแล้วนั่นคือเป้าหมายที่แท้จริงของหลักการทั้งหมดในเอกสารนี้ — โค้ดถูกเขียนเพื่อมนุษย์ก่อน แล้วจึงเพื่อเครื่องจักร
