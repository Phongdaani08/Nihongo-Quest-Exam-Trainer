# Public Dashboard Sharing

## Problem Statement

A Dashboard Owner can create a Public Dashboard Share, but a Public Dashboard Viewer currently receives an empty page even when the public API returns Dashboard data. The page renders chart data as plain label/value rows, expiration controls do not persist a real deadline, and share tokens are generated from predictable time-derived state.

## Solution

Provide a standalone, unauthenticated, read-only Public Dashboard Viewer that resolves the Next.js route token correctly, validates the public Dashboard contract, and renders the same chart visualizations as the authenticated Dashboard. Let the Dashboard Owner configure an optional future expiration and generate every new share token with an operating-system cryptographic random source.

## User Stories

1. As a Dashboard Owner, I want to create a Public Dashboard Share, so that people without AI GenBI accounts can view my Dashboard.
2. As a Public Dashboard Viewer, I want the link to open without Login, so that public sharing is frictionless.
3. As a Public Dashboard Viewer, I want the entire page dedicated to the Dashboard, so that application navigation does not distract from the shared content.
4. As a Public Dashboard Viewer, I want charts to use the same visual renderer as the authenticated Dashboard, so that the public representation is faithful.
5. As a Public Dashboard Viewer, I want KPI values and table panels to remain readable, so that every supported Dashboard panel has a useful representation.
6. As a Public Dashboard Viewer, I want the page to be read-only, so that possession of a public token never grants mutation rights.
7. As a Public Dashboard Viewer, I want a clear unavailable message for an invalid or revoked link, so that failure is understandable without leaking Dashboard details.
8. As a Public Dashboard Viewer, I want a clear expired message, so that I know to request a new link.
9. As a Dashboard Owner, I want to configure whether a Public Dashboard Share expires, so that access can be time-bounded.
10. As a Dashboard Owner, I want to select a future expiration date and time, so that the deadline is explicit.
11. As a Dashboard Owner, I want an invalid or past expiration rejected, so that the system never silently creates a non-expiring link.
12. As a Dashboard Owner, I want the modal to reflect the expiration already saved, so that reopening it shows the actual state.
13. As a Dashboard Owner, I want disabling a public link to block it immediately, so that I can suspend access.
14. As a Dashboard Owner, I want revoking a link to invalidate its token, so that an old URL cannot be reused.
15. As a security reviewer, I want tokens generated by a cryptographically secure random source, so that public links cannot be predicted from creation time.
16. As a security reviewer, I want the backend to remain the authority for enabled, expired, and revoked states, so that UI changes cannot bypass access rules.
17. As a developer, I want public API data validated before rendering, so that malformed panels cannot crash the page.
18. As a developer, I want the Public Dashboard Viewer to reuse the existing chart renderer, so that chart behavior does not diverge between authenticated and public pages.

## Implementation Decisions

- A Public Dashboard Viewer is an unauthenticated access mode, not a Dashboard Access Role and not a Tenant member.
- Public access remains isolated behind a GET-only token endpoint. Authenticated Dashboard mutation endpoints never accept a public token.
- The dynamic route resolves its asynchronous parameters at the server boundary and passes a plain token to a client Public Dashboard Viewer component.
- Public Dashboard API responses use concrete KPI and panel types and are runtime-validated before rendering.
- The Public Dashboard Viewer reuses the existing Dashboard chart renderer rather than maintaining a second chart implementation.
- Public Viewer capabilities are centralized: view is always permitted for a valid share, export follows the share flag, and all mutations and share management are denied.
- Expiration is optional. When enabled it must be a valid future UTC instant. Invalid and past values are rejected rather than interpreted as no expiration.
- Public share tokens use an operating-system cryptographic random source and a URL-safe representation with at least 128 bits of entropy.
- The existing database token column and API paths remain unchanged to minimize migration and integration risk.
- Revocation continues to create a new token if a Public Dashboard Share is later recreated.

## Testing Decisions

- Tests verify observable behavior through public component, validation, service, and PostgreSQL-backed sharing interfaces.
- A route-boundary test verifies that an asynchronous Next.js parameter reaches the Public Dashboard Viewer as a plain token.
- Frontend tests cover contract validation, read-only capabilities, and expiration serialization.
- Backend tests cover cryptographic token shape and uniqueness, future expiration persistence, rejection of invalid or past expiration, and enabled/expired/revoked access.
- An HTTP-level regression check verifies that an active token returns Dashboard content without a Login session and that the standalone page requests that token.

## Out of Scope

- Browser Fullscreen API behavior that hides browser tabs and the address bar.
- Password-protected public links.
- Per-link analytics and viewer identity tracking.
- Email delivery of public links.
- Storing only a one-way token hash; raw-token-at-rest hardening can be introduced separately if link recovery requirements change.
- Redesigning the authenticated Dashboard editor.
